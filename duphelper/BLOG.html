The Helper You Already Had

A one-line pointer-of helper got rewritten under a new name in a sibling file, in the same package, where the original was already sitting — twice in one review. Neither gofmt nor go vet nor staticcheck has anything to say about it, because nothing about either declaration is individually wrong. The problem only exists in the relationship between the two.

slopless-go · duphelper · go/analysis

It looked like this. A test file needed a way to turn a float64 into a *float64 for a fixture field: 

func ptrFloat64Widget(w float64) *float64 { return &w }

Reasonable-looking code, in isolation. The problem is that a sibling file in the exact same package already had this: 

func ptrFloat64(v float64) *float64 { return &v }

Same signature, once you look past the parameter's name. Same body, once you look past the local variable's name. One of these two declarations does nothing the other doesn't already do — most likely it was added to dodge a ptrFloat64 redeclared in this block compiler error, or simply because the existing one wasn't noticed two files over.

01Why nothing else catches this

Static duplication is boring to look for by hand and easy for a linter to get wrong. Token-clone detectors (the dupl family) hunt for *similar* blocks anywhere in a file, tuned with a token-count threshold — useful for flagging a copy-pasted 40-line method, noisy on anything smaller, and blind to the specific thing that makes this case actionable: the two declarations are structurally identical, in the same package, which means one of them can just be deleted. That's a much narrower, much more confident claim than "these two blocks look alike."

duphelper is built for exactly that narrower claim. It walks every hand-written top-level function in a package, and for each pair whose signature matches by type (parameter and result names ignored) and whose body is alpha-equivalent (identical once every local is replaced by a position-keyed placeholder instead of its literal name), it reports the later one, pointing back at the first.

02Position, not order

The first version of this compared bodies by renaming each local to a placeholder in the order it was first read. That's wrong, and it took a second, deliberately adversarial pair of test functions to see why: 

func clampLow(a, b int) int {
    if a < b {
        return a
    }
    return b
}

func clampHigh(a, b int) int {
    if a < b {
        return b
    }
    return a
}

Renamed by first-use order, both bodies read identically: "compare the first-seen local against the second-seen local; branch returns the first-seen one; fallthrough returns the second-seen one." The two functions compute genuinely different things — one clamps low, one clamps high — but a first-use renaming scheme can't see that, because it never distinguishes which parameter a placeholder stands for, only which one got mentioned first.

The fix: bind parameters and named results to their placeholders by declared position, before the body is walked at all — a is always the first placeholder, b always the second, regardless of which one either function happens to read first. Only after that binding is fixed does the body get walked, and any *further* local — a :=, a var, a range variable — gets the next placeholder in the order it's first declared. clampLow and clampHigh now render to two different strings, and stay uncollapsed.

☝ Every finding is a candidate, not a verdict. A short, identical-looking pair can still be intentional, and duphelper doesn't know why a function was split out any more than a human skimming a diff does. What it buys you is not having to notice the pair exists in the first place.

03Where it stops looking

It's a single-package pass, so the most common real miss is the cross-package case: a private reimplementation of something that already exists as an exported helper in an imported helpers package. Catching that would mean exporting a fingerprint as an analysis.Fact along the import graph — a real extension, not attempted in this first pass. Methods and generic functions are left alone too, for the same reason singlecaller leaves exported symbols alone: comparing them correctly needs more context than a single package gives you.
