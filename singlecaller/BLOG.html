The One-Caller Trap

A helper function copied from a proven pattern, a reviewer asking "wait, who else calls this?", and a small static-analysis tool built to ask that question automatically — plus the false positives that taught it some manners. (Examples below are a small, self-contained demo built for this post, not excerpts from any real codebase.)

Backend / tooling · ~8 min read · Go, go/analysis

It started with a small builder function, copied from a pattern that was already working well elsewhere in the same codebase. Not an unusual move — most of a CRUD-shaped service is the fourth or fifth repetition of something, and copying the third one's structure and swapping the nouns is normal, healthy reuse. Except this time the thing being reused didn't actually apply.

The pattern in question is a small conversion layer, the kind almost every Go service that talks to a database ends up with: a code generator (sqlc, ent, sqlboiler, hand-rolled scanning — take your pick) produces a distinct Go struct for every SQL query's result row, and a one-line builder turns that row into the domain type the rest of the app actually works with. For one entity — call it Order — that builder is orderFromFields, and it earns its keep honestly: ListOrders, GetOrder, CreateOrder, and UpdateOrder each produce their own distinct row type, and all four need converting the same way. One builder, four callers, zero duplication.

A neighboring entity — call it Customer — got the same treatment: a private customerFromFields builder, called from a GetCustomer wrapper, exactly like its Order counterpart. It compiled. It worked. It also, as it turned out, had exactly one caller — because every one of Customer's queries happens to return the very same row type. There was never a second shape to reconcile.

01Fan-in is the whole story

The pattern isn't wrong in the abstract — it's wrong for Customer specifically, and the reason is entirely about how many distinct callers actually exist. Here's the same shape, side by side, with the caller count that makes one version earn its place and the other version pointless:

The fix, once you see it that way, is a one-line inline — replace the call with the struct literal it was always going to build, and delete the middleman. That's a two-minute change. The more interesting question is the one that came up right after:

"Can a linter catch this so we don't have to notice it by hand next time?"

02Why go vet shrugs

The instinctive answer is unused — staticcheck's dead-code checker, a standard entry in most golangci-lint configs. It doesn't apply here, and the reason matters: customerFromFields isn't dead. It's called. Exactly once, but once is not zero, and "used" is precisely the bar unused checks.

Widen the search and the same problem shows up everywhere — gocritic, revive, unparam — because a rule like "flag any unexported function with one caller" would be actively bad advice applied blindly. Breaking a long function into a named, single-use piece is often exactly the right move for readability. A linter that punished every one-caller extraction would train people to stop doing that, which is a worse codebase than the one with an occasional unnecessary builder in it.

What actually made customerFromFields wrong wasn't "one caller" as an abstract fact. It was that the reason the pattern existed — reconciling several distinct row shapes — didn't hold for Customer. No linter can know that without understanding how this particular codebase generates row types, which is exactly the kind of repo-specific context a general-purpose tool shouldn't try to encode. So instead of forcing this into an existing linter's rule set, it became a purpose-built tool: small, honest about what it can and can't judge, and easy to run as one more check in the pipeline.

03What the tool actually does

go/analysis — the framework behind go vet itself — turns this into a short program. Give it a package, and it hands back full type information: every identifier's declaration (Defs) and every place that identifier gets used (Uses), already resolved across files. That's the whole trick: don't grep for a function name in text, walk the type-checked syntax tree and count.

The whole analyzer is short enough to read in one sitting:

var Analyzer = &analysis.Analyzer{
    Name: "singlecaller",
    Doc:  "reports short, unexported funcs/methods called from exactly one site",
    Run:  run,
}

// declared: every unexported FuncDecl short enough to matter.
// counts: every *types.Func a CallExpr actually resolves to.
// callerComplexity: the branch count of whichever function that
// one call came from.
for obj, d := range declared {
    if counts[obj] != 1 {
        continue
    }
    if cc := callerComplexity[obj]; cc > maxCallerComplexity {
        continue
    }
    pass.Reportf(d.node.Pos(), "%s is called from a single site (call site complexity %d)", d.name, cc)
}

Point the very first version — just "unexported, one caller, full stop," no other rules — at even a small, otherwise unremarkable service and it finds the exact bug that inspired it, plus a handful of other things that are technically true and practically useless. Here's a compact stand-in service — eight unexported functions, one main/run pair, a couple of HTTP handlers, a background loop — run through that first, unrefined version:

04Eight hits, two of them obviously wrong

entities.go:68:1:  customerFromFields is referenced from a single place
service.go:29:1:   run is referenced from a single place
service.go:91:1:   buildServer is referenced from a single place
service.go:101:1:  newTimeoutSeconds is referenced from a single place
service.go:112:1:  healthHandler is referenced from a single place
service.go:125:1:  handleLogin is referenced from a single place
service.go:134:1:  sanitizeRedirectPath is referenced from a single place
service.go:144:1:  sweepExpired is referenced from a single place

Two of these are obviously wrong the moment you read them. run() is referenced exactly once, from main() — because that's what a main() is for, not because it's a pointless wrapper. handleLogin is referenced exactly once too, but that reference is mux.HandleFunc("/login", handleLogin) — a bare value handed to a router, invoked later by the HTTP mux, not by any line of code the analyzer could point at as "the one call site." Flagging either isn't technically wrong — the naive version's rule really is "one reference, full stop" — but it's useless. There's nowhere sensible to inline a route handler into, and no version of "inline run() into main()" makes anything simpler.

Two adjustments cut the noise.

Only count direct calls. A reference used as a value — passed to a router, handed to go as an argument, stored in a struct field — isn't a call the tool can reason about inlining. So the walk narrowed from "every identifier that resolves to one of our declared functions" to "every *ast.CallExpr whose callee resolves to one of them." That alone drops handleLogin — a bare reference — out of the results, while correctly leaving healthHandler in: its one reference is healthHandler(store), a real call that produces the handler value, not a bare name.

Only flag short functions. A single-caller function well over a page long is almost never the "just inline the struct literal" pattern this tool is hunting — it's a deliberate readability split, and inlining it would make the caller worse, not better. A 15-line ceiling (maxInlinableLines in main.go) keeps the tool aimed at the trivial-builder shape it's actually good at recognizing, and quiet about run(), which is long enough on its own to clear the bar regardless of how it's referenced.

Same demo, same command, after both changes:

6 findings — down from 8. run() dropped for being long; handleLogin dropped for being a value, not a call.

05Six findings, most of them fine

Six is a number you can actually read, one at a time, which is the whole point — the tool's job is to shrink the list a human has to look at, not to replace looking. Here's what the six turned out to be:

  • customerFromFields — the original bug. No independent meaning, one caller, nothing to reconcile. Should be inlined.
  • newTimeoutSeconds — four lines, an if on an environment string, no independent meaning whatsoever. Should be inlined.
  • sanitizeRedirectPath — an explicit open-redirect guard. Short, single-caller, and shaped exactly like the two functions above — but this one is worth keeping separate regardless of caller count, because burying a security check inline makes it harder to audit later.
  • sweepExpired — a background loop launched with go sweepExpired(...). Inlining a ticker-and-select loop into whatever launches it helps no one.
  • buildServer — a small constructor. Reasonable either way, honestly — one caller, but a name that documents "this is where the server gets assembled" is worth something too.
  • healthHandler — the standard Go "handler factory" pattern: called once, directly, to produce the closure the mux actually serves. Kept separate for route-table readability by convention, not by accident.

Two out of six. That ratio is the actual finding here, more than the tool itself: a linter can point at candidates, but distinguishing "nobody needed this" from "this is a named security check that happens to have one caller" is squarely a human judgment call, every time — customerFromFields and sanitizeRedirectPath are the same shape by every measure the tool takes (short, unexported, one direct call), and only one of them should exist. The tool's heuristics — direct calls only, short bodies only — get the list from eight to six. They can't get it to two. Nothing short of understanding the code can.

💡 The takeaway isn't "write more precise heuristics." It's that a tool like this is a search-space reducer, not a verdict machine — which is exactly why it's wired in as advice, not as a gate.

06One more axis: how complex is where it lands

A fair question came up after this shipped: the tool judged whether the candidate was short enough to bother inlining, but never looked at how much was already going on wherever it would land. A four-line helper is trivially inlinable into a five-line function. It's a different proposition dropped into a function that's already juggling a dozen branches — the result isn't simpler, it's just moved the same complexity from a named place to an anonymous one.

The fix is the same shape as the first two refinements: measure something cheap and structural, then use it as one more filter. go/analysis already has the AST in hand, so counting a function's cyclomatic complexity — one point for every if, for, non-default case, &&, or || — is about a dozen lines, the same McCabe-style count tools like gocyclo report.

Run it against the same six survivors, complexity ceiling disabled just to see the numbers:

sweepExpired   — call site complexity 16  (run, the service's start/stop lifecycle)
buildServer    — call site complexity 16  (run, same caller)
healthHandler  — call site complexity 16  (run, same caller)
sanitizeRedirectPath — call site complexity  1  (handleLogin)
newTimeoutSeconds    — call site complexity  1  (buildServer)
customerFromFields   — call site complexity  1  (GetCustomer)

One detail worth noticing before the ceiling even comes into it: three of these six trace back to the exact same caller. run() — the service's entire start/stop lifecycle, with its config validation, its signal handling, its shutdown sequence — is where all three land, so all three inherit its complexity equally, whether they're a handler factory, a background loop, or a constructor. One overloaded call site retroactively puts every one of its direct calls under the same scrutiny.

A ceiling of 15 — comfortably above what a clean, single-purpose function should ever need — cuts all three (sweepExpired, buildServer, healthHandler) out automatically. All three were already on the "keep separate, or at least defensible" side of the manual review above, for reasons this check knows nothing about — a background loop, a named constructor, an idiomatic handler factory. The complexity check didn't arrive at that conclusion for those reasons. It arrived at the same conclusion for a completely different one, which is the best a second heuristic can really do: agree with judgment already made, on cases nobody's looked at yet. 

3 findings — down from 6, with zero additional human judgment spent on the three that left.
💡 This doesn't undo the earlier point about heuristics not replacing judgment — it adds a structural signal, not a smarter one. "How branchy is the landing spot" is answerable straight from the AST; "does this deserve to be named" still isn't, and the tool still says nothing about the two of the final three that are worth acting on.

07Advisory, everywhere it runs

Given that ratio, blocking anything on this check would be the wrong call — it would either train people to silence a mostly-correct tool, or worse, get people inlining security checks just to make CI green. So it runs in three places, and none of them stop you:

This repo's own .githooks/pre-commit (set up once with git config core.hooksPath .githooks) skips entirely unless a staged file is a .go file, so it costs nothing on a docs commit. Its CI step runs with continue-on-error: true — visible in every build log, blocking nothing. Both are about a dozen lines; see .githooks/pre-commit and .github/workflows/ci.yml at the repo root.

The whole arc fits in one sentence: a copy-pasted pattern that quietly stopped making sense, a question about whether tooling could have caught it, and a small analyzer that keeps answering a little more precisely each time it's asked a follow-up — eight hits down to six by only counting real calls and ignoring long functions, six down to three by asking how complex the landing spot already is. On a real, much larger codebase, expect all three numbers to be bigger — but the shape of the narrowing, and the fact that a human still reads whatever's left, doesn't change with scale. That narrowing is the actual deliverable, not the tool itself. A linter that returns eight or even six confident-sounding candidates teaches people to ignore it; one that keeps shrinking the list, and stays honest that a human reads whatever's left, gets to stick around.
